# Glitch — AI 서버 계약 논의 안건 (갱신)

백엔드(몸통) ↔ AI 서버 · 2026-10-29 갱신 (2026-10-13판 `ai-contract-agenda.pdf`를 대체)
"현재 동작"은 `pre-deploy` 브랜치 기준이다. **결정** 표시는 백엔드 쪽에서 정해 반영한 것이고, 나머지 잠정안은 AI 담당과 확정할 것이다.

## 0. 백엔드 쪽 방향 — AI 담당에게 먼저 확인받을 것

> **AI 서버는 상태를 갖지 않는다. 모든 분석 자료(캐논, ID, 사건 임베딩)는 백엔드 DB에 저장한다.**
> AI 서버에는 DB가 없고, 지금 쓰는 `Data/stories/` 파일 상태(`ep_global`, `event_embeddings.json`)는
> 백업·소유권 검사·삭제·버전 관리 밖에 있다. AI 서버는 요청마다 몸통이 보낸 스냅샷·델타·임베딩으로 일하고 아무것도 남기지 않는다.
> 2차 검수 때 몸통이 과거 사건의 임베딩을 함께 보내고, **받은 임베딩은 임베더에 다시 넣지 않는다**.

이 방향이면 1-1 = (a), 1-3 = (a)로 정해지고 2-1·2-5·4-4·4-5가 따라 풀린다. 남는 계약 문제는 7장.

## 7. 상태 없는 AI 서버 — 임베딩은 몸통 DB에 *(배포 뒤 작업)*

**왜 몸통 DB인가:** AI 쪽 캐시로 두면 작품 삭제·사용자 간 분리·동시 쓰기를 AI 서버가 따로 관리해야 한다. 0장 원칙과 어긋난다.
몸통에 두면 작품 삭제(CASCADE)·소유권·백업이 그대로 적용되고, AI 서버를 여러 대로 늘려도 된다.
같은 모델·정밀도면 같은 문장은 같은 벡터가 나온다고 보지만(BGE-M3), fp16(시연 PC)↔fp32 차이가 Top-K에 영향을 주는지는 **측정하지 않았다**.

| # | 정할 것 | 잠정안 |
|---|---|---|
| 7-1 | 임베딩을 누가 계산하나 | AI 서버. 몸통에는 모델을 두지 않고 값만 저장한다 |
| 7-2 | 몸통 저장 | 새 테이블 `event_embeddings(project_id, model, content_hash, vectors)`. **원문 해시가 키**이고 캐논 버전과 묶지 않는다(같은 원문 = 같은 벡터). 작품 삭제 시 CASCADE |
| 7-3 | `content_hash` | 사건 `title`(캐논 `label`)·`summary`·`cause`·`result`의 해시. 계산 함수는 양쪽이 공유하는 `interface.py`에 하나만 둔다 |
| 7-4 | 보내는 것 | 검수 요청에 스냅샷·델타 사건의 해시에 맞는 임베딩 `{model, content_hash, vectors}`를 싣는다. 전송은 float16 + base64(사건 1건 ≈ 8KB, 300건 ≈ 2.4MB) |
| 7-5 | AI 동작 | `model`·`content_hash`가 맞으면 **그대로 쓰고 임베더에 넣지 않는다**. 없거나 모델이 다르면 계산한다 |
| 7-6 | 돌려받는 것 | `ReviewOutput.embeddings`에 새로 계산한 것만. 몸통은 응답을 받을 때 바로 upsert(캐논 병합과 무관 — 파생값이라 save 트랜잭션을 기다리지 않는다) |
| 7-7 | ID 통합도 상태 없이 | AI가 스냅샷의 인물(이름·`attrs.aliases`)·장소와 `entity_key`로 새 항목을 맞춘다. 새 키는 스냅샷의 `CHAR_###` 등 순번 키의 최대값 다음. 해시 키(`char-…`)는 순번 계산에서 빼고, 처음 보는 키도 그대로 받아들인다 |
| 7-8 | `scope_ai` 업스트림과의 관계 | `scope_bridge`가 요청마다 스냅샷·델타·임베딩으로 임시 상태를 만들어 `scope_ai`에 넘기고 끝나면 버린다. 업스트림을 고칠지는 AI 담당이 정한다 |

**몸통 작업량(예상):** 마이그레이션 1개(7-2) · 해시 함수 · `interface.py`의 `ReviewOutput.embeddings` 추가 · 검수 작업에서 임베딩 실어 보내기·응답 저장 · 테스트(내용이 그대로면 재계산 요청이 없는지, 작품 삭제 시 임베딩도 지워지는지).
